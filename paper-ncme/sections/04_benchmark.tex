\section{Putting it to the test}
\label{sec:benchmark}

To show the approach works beyond a single example, we evaluate on \GeoGenBench, 801 prompts, all scored automatically by the checker of \cref{sec:scoring}. Six hundred come from the templates described above; another 201 are drawn from a real K--12 mathematics curriculum \citep{bluebonnet2024}. The prompt set, templates, checker vocabulary, and rendered outputs are public.\footnote{\url{https://huggingface.co/datasets/meix/geogenbench}} We ran six large models from three companies, each in two modes: writing drawing code by hand, and using the structured description. Throughout, a \emph{pass} means passing that automatic checker; since the checker is one-directionally lenient (\cref{sec:scoring}), the rates below are optimistic ceilings on true geometric correctness, not exact-correctness rates.

\paragraph{How we ran it.}
The by-hand baseline asks the model to write TikZ drawing code directly; the structured mode fills in the typed form of \cref{sec:pipeline}. Both modes run at temperature $1.0$, with no explicit output-token limit and the \emph{same} budget of up to three attempts---what differs is the retry trigger. The baseline retries only when its code fails to render; the structured mode also retries when its description fails to compile or the figure breaks a check it declared. Those declared checks are the model's own, though: the held-out scoring predicates the item template generates---the ones we actually grade against---are never fed back to it. The structured advantage is therefore not more attempts but more feedback---it lets a model catch its own geometric mistakes, which hand-written code cannot, and those extra retries show up in its per-item cost. The $600$ templated prompts divide evenly across three difficulty tiers ($200$ each), generated from $30$ construction templates---triangles, quadrilaterals, circles, segments, and lines---with $3.2$ requirements apiece on average; the $201$ curriculum prompts were written from the topic scaffold of a public K--12 geometry curriculum (drafted with a language model, answer keys written by hand) and carry more, $6.0$ on average. Cost per item is the prompt's token count, summed across any retries and priced at each vendor's published rates, averaged over every prompt, failures included.

The structured approach helped \emph{every} model (\cref{tab:results})---and helped the weakest ones the most, raising pass rates by anywhere from 2 to 25 percentage points. In other words, handing a model the geometry engine matters most when the model is poor at drawing by hand. More striking still: once they used the structured approach, the three strongest models landed within a single point of one another, even though they differ sevenfold in price. On this task, the method does more of the work than the model does.

Because the checker errs in one direction only, the human study of \cref{sec:scoring} lets us correct these ceilings. Of the automatic passes the graders rated (diagrams from a pilot run of the same benchmark), they confirmed 75\% of those drawn by hand (86 of 114) and 87\% of those drawn from the structured description (55 of 63); the checker never failed a diagram the graders passed. Read that way, the true structured rates in \cref{tab:results} are roughly seven-eighths of those shown and the by-hand rates roughly three-quarters. The structured advantage survives the correction and widens: the description reduces not only the failures the checker catches but the silent errors it misses. The per-model cells in that study hold 7 to 23 diagrams, too few to correct each row separately.

We also hit one practical snag worth flagging for anyone building something similar. Gemini~2.5~Flash could not run the structured mode at all. The likely cause is not model ability but the vendor's decoding machinery: when a schema is supplied, the API compiles it into a finite-state constraint on the output, and our form, with its 31 kinds of building block, compiles to more states than Flash's serving tier allows. The request was rejected before any token was generated, with the message that the schema ``produces a constraint that has too many states for serving.'' Gemini~2.5~Pro and the OpenAI models accepted the same schema. Per-template results, cost breakdowns, and failure analyses appear in the companion paper.
